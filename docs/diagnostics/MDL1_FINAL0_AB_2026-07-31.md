# MDL.1 — Beat This! `final0` vs `small0`: offline A/B

**Increment:** MDL.1 (beat-sync program, D-202) · **Decision:** D-E
**Date:** 2026-07-31 · **Recommendation: DO NOT ADOPT**

---

## Why this ran now

DBN.2 ended with a specific finding: with an unbiased decoder, odd meters are won by
hairline margins and money/take_five still decode as 4 — **the remaining gap is evidence
quality, not model bias** (`DBN_DECODER_SPEC.md` §9.7). `final0` is the only lever in the
program that changes the evidence itself rather than how it is read, and the plan expected
its leverage on exactly suites 2 and 4. So this is the direct test of that finding.

## Setup

- **Checkpoint:** `beat_this-final0.ckpt`, already on disk from DSP.2 (81,058,141 bytes). No
  download was needed.
- **Conversion:** the existing `Scripts/convert_beatthis_weights.py`, which already supported
  `--variant final0`. Output: 161 tensors, **20,253,104 params / 81,012,416 bytes** — matching
  the plan's "20.3 M params / 81 MB".
- **Architecture delta:** exactly one hyperparameter. `transformer_dim` 128 → 512, which drives
  embed dim 128 → 512, head count 4 → 16 (head_dim stays 32) and FFN 512 → 2048. `n_layers`,
  `stem_dim`, `spect_dim` are identical. So this is a parameterisation, not a second
  architecture — implemented as `BeatThisModel.Variant`.
- **Weights are NOT vendored.** 81 MB does not enter the bundle before D-E decides;
  `BeatThisModel(device:variant:weightsDirectory:)` loads them from an external directory.
- **Ran through the real MPSGraph path**, not the PyTorch reference, because D-E asks about
  **prep latency** and only the shipping path can measure that.

## Results — 9 ground-truthed tracks

`ratio` = downbeat peaks / beat peaks, DBN.1's degeneracy metric. Lower is better: it means
fewer beats are marked as candidate bar lines.

| track | truth | small0 meter | final0 meter | small0 ratio | final0 ratio |
|---|---|---|---|---|---|
| billie_jean | 4 | **4 ✓** | **4 ✓** | 0.24 | 0.32 |
| money | 7 | 1 ✗ | 1 ✗ | 0.90 | **0.59** |
| solsbury_hill | 7 | 1 ✗ | 1 ✗ | 0.69 | 0.87 |
| take_five | 5 | 2 ✗ | 2 ✗ | 0.41 | 0.58 |
| bohemian_rhapsody | 4 | 2 ✗ | **4 ✓** | 0.41 | 0.31 |
| bleed | 4 | **4 ✓** | **2 ✗** | 0.31 | 0.37 |
| pyramid_song | — | 1 | 3 | 0.69 | 0.38 |
| yyz | — | 2 | 2 | 0.47 | 0.54 |
| clair_de_lune | — | 3 | 3 | 0.31 | 0.32 |

| | meter correct | mean ratio | mean inference |
|---|---|---|---|
| **small0** (8.4 MB) | **2 / 6** | 0.494 | 131 ms |
| **final0** (81 MB) | **2 / 6** | 0.475 | 200 ms |

## Reading

**No meter improvement.** 2/6 both. final0 *gains* bohemian_rhapsody and *loses* bleed — a
trade, not a win. Every odd-meter track (money 7, solsbury_hill 7, take_five 5) is still wrong
under both.

**The degeneracy is not fixed.** Mean ratio 0.494 → 0.475 is a 4 % move, and it is not
consistent: money improves markedly (0.90 → 0.59) while solsbury_hill (0.69 → 0.87) and
take_five (0.41 → 0.58) get worse. **This is the decisive number** — DBN.2 established that the
blocker is evidence quality, and a 10× larger model of the same family does not supply it.

**A regression on the category-4 track.** `bleed` is *the* suite-4 case, and the plan expected
final0 to help there. Under final0 its BPM doubles (115.00 → 259.43) and the meter goes 4 ✓ → 2 ✗.
`yyz` also flips (246.74 → 124.39, a halving; truth is 272.27, so small0 was closer).

**Cost.** ~10× the weights (8.4 → 81 MB) and ~1.5× the mean inference. The billie_jean rows
(792 / 1371 ms) include first-call graph warm-up; steady-state is ~40–60 ms for small0 and
~50–70 ms for final0, so the real inference penalty is ≈1.3×.

## Caveat, stated rather than buried

**The final0 port is not independently verified.** DSP.2 S8 established the layer-match
methodology — dump the PyTorch reference's per-stage activations and assert per-boundary — and
there is a fixture set for small0 but none for final0. This A/B therefore assumes the conversion
and the MPSGraph path are correct for the larger dims.

Two things make a gross error unlikely: the refactor is verified behaviour-preserving for
small0 (all 26 `BeatThis*` tests pass, including the layer-match suite that caught four bugs in
DSP.2 S8), and final0's BPMs closely track small0's on most tracks (102.68 vs 102.68 on
solsbury_hill, 116.88 vs 116.94 on billie_jean, 169.24 vs 169.35 on take_five) — noise from a
broken port would not agree to three significant figures.

But it is not proof. Since the result is **negative**, a port bug would only matter if it were
masking a real improvement. If D-E goes against this recommendation, build the final0
layer-match fixture first (needs `beat-this` + the pinned repo in a torch venv) rather than
adopting on this evidence alone.

## Recommendation

**Do not adopt.** 10× the weight size and ~1.3× the inference cost buy no meter improvement, no
consistent evidence improvement, and a regression on the category-4 track the plan expected it
to fix.

The corollary matters more than the decision: **the evidence ceiling DBN.2 hit is not a
capacity problem.** Scaling the same model family does not produce a cleaner downbeat stream, so
categories 2 and 4 need a different premise — a different model family, a different training
target, or accepting that the downbeat stream cannot carry meter and getting bar position from
somewhere else entirely.

## Reproduce

```bash
~/phosphene-ml-env/bin/python Scripts/convert_beatthis_weights.py \
  --checkpoint ~/.cache/torch/hub/checkpoints/beat_this-final0.ckpt \
  --variant final0 --out /tmp/beat_this_final0

PHOSPHENE_MDL1_AB=1 PHOSPHENE_FINAL0_DIR=/tmp/beat_this_final0 \
  swift test --package-path PhospheneEngine --filter Final0AB
```
