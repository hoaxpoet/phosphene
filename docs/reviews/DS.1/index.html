DS.1 — the app adopts UzumeTokens

Presentation only. Nothing the user can do changed: no state machine, publisher, view model, accessibility identifier, copy string, keyboard shortcut or test expectation was touched. Every pair below is the same screen at the same window size, before and after the token swap.

before is main at caa69638. after is the DS.1 branch. Uzume is always dark (D-231 option A), so there is one appearance to review. This Mac is set to Light appearance, which is why the window chrome changes.

Twelve of twenty states are captured. Eight are not: four need a live connector credential, a failing track or a revoked permission grant to reach at all, three are Settings sub-panes that hold no retokenized code, and one (Ready) is passed through faster than the local-file route can be sampled. Each says so under its own heading.

Idle

Three changes. The canvas moves from pure black to --color-canvas #0b0c10 — a warmer near-black, clearest against the window chrome. The wordmark takes --color-text-primary (ivory #f4f6f1, not pure white) and the secondary action takes --color-text-tertiary. And the window is pinned dark: this Mac is set to Light appearance, so before, the title bar was light grey and the primary button was system blue. The primary is now Uzume violet and the secondary is still quiet grey — that is the scoped tint you asked for.

Source picker

Connector tiles move from Color.white.opacity(0.07) / 0.03 to --color-surface-raised / --color-surface, which land within a level or two of what the translucent fills produced over black. Corner radius 12 is now --radius-md. Note the disabled-tile regression is not visible here because all three sources are enabled; where it does appear, --color-text-disabled and --color-text-tertiary are the same value, so disabled reads slightly brighter than it did (upstream finding 8).

Canvas and the text ramp. Unrelated bug spotted while capturing: the status line reads “Checking every 2 secondsu2026” — a literal u2026 where an ellipsis should be, in both before and after. It is a copy string, so DS.1 left it alone; worth its own fix.

Spotify connection

Canvas, the four white@0.07 panels onto --color-surface-raised, and the inline status marks onto --color-success / --color-warning. The playlist TextField and its buttons stay native.

Preparation (in progress)

Canvas; the aggregate progress track moves to --color-surface-selected and its fill to --color-text-secondary; the row divider to --color-line-subtle. Track status icons take the success / warning / danger roles — the danger role is a warm salmon #ff8a75, not systemRed.

Settings — Local Files

Nothing in Settings was retokenized — it held no hard-coded values. What this pair shows is the appearance pin. The sidebar selection is still system blue and I could not change it. macOS draws List sidebar selection from NSColor.controlAccentColor — the system-wide Accent colour in System Settings → Appearance — and SwiftUI's .tint() does not override it. Verified twice: blue with the tint on this List, and blue in the earlier build that tinted the entire app. The only way to make it violet is to draw the selection ourselves, which is exactly the 'do not redraw native macOS controls' rule COMPONENTS.md sets. Recorded as a finding rather than forced.

Ended

The orange you spotted is the before column. EndedView carried its own coralAccent — a hard-coded Color(red: 0.97, green: 0.45, blue: 0.36) from the retired coral direction, with a .tint() on the primary CTA. The after column was already violet, but only because .uzumeTint() sits closer to the Button than the coral tint does — ordering luck, not a decision. The constant and its tint are now deleted.
